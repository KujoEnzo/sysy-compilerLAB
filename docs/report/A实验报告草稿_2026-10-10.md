## 摘要

以迭代阶乘为例，观察预处理、编译、汇编和链接的阶段产物，并利用 Clang 的 token、AST 与 LLVM IR 输出分析程序表示的变化。对阶乘函数执行 mem2reg 后，三个局部存储槽及相关 load/store 被两个循环 phi 和直接 SSA 值使用替代。另构建调用 SysY 输入输出接口的手写 LLVM IR 路线，在 RV64 Linux 环境下通过 QEMU 与源程序进行对照。五组输入在宿主源程序、优化前后参考 IR、RV64 源程序及 RV64 手写 IR 路线中均得到预期阶乘结果，退出码均为 0。实验结果支持所列测试下的行为一致性，不构成全部输入的形式化等价证明或性能结论。

关键词：编译阶段；LLVM IR；SSA；mem2reg；RISC-V；SysY 运行库

## 实验目的

区分编译流程中的各类产物，理解源程序、AST、LLVM IR 与汇编之间的对应关系；通过循环 phi 和局部变量提升观察 SSA 表示；验证手写 IR 与 C 运行库在 RV64 下的衔接，并使用预先确定的输入输出检查程序行为。

## 实验方法与结果

### 源程序与基准验证

采用带独立 `fact(int n)` 函数的迭代阶乘程序，覆盖变量、赋值、乘法、比较、循环、参数与返回值。循环变量从 2 开始，累乘结果初始化为 1；在 `i <= n` 时更新结果并递增循环变量。`main` 使用 `scanf` 读取整数，以 `printf` 输出结果及换行。输入范围限制为 0 至 12，避免 32 位有符号整数溢出。

对宿主机可执行文件 `build/host/fact` 进行了如下测试，实际输出来自 Ubuntu 终端记录：

| 输入 | 预期输出 | 实际输出 | 退出码 |
| --- | --- | --- | --- |
| 0 | 1 | 1 | 0 |
| 1 | 1 | 1 | 0 |
| 5 | 120 | 120 | 0 |
| 10 | 3628800 | 3628800 | 0 |
| 12 | 479001600 | 479001600 | 0 |

五组结果与预期一致。输入 0 和 1 时，循环条件首次判断即为假，返回初始值 1；其余输入验证了正常迭代和选定测试域的上界。这些结果确认程序通过所列测试，不等同于穷尽验证所有可能输入，也不是 RISC-V 目标程序的运行结果。

测试记录保存位置：实验目录中的 `logs/a/fact-baseline.txt`。

### GCC 编译阶段观察

按预处理、编译、汇编和链接顺序组织构建：

```bash
gcc -E src/fact.c -o build/host/fact.i
gcc -S build/host/fact.i -o build/host/fact.s
gcc -c build/host/fact.s -o build/host/fact.o
gcc build/host/fact.o -o build/host/fact
```

`file` 检查结果如下：

```text
build/host/fact.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
build/host/fact:   ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=bd43627594522afc6697a78e83dccbbb37d7d3cb, for GNU/Linux 3.2.0, not stripped
```

目标文件为 x86-64 可重定位 ELF，而链接结果为 x86-64 的位置无关可执行文件（PIE），采用动态链接，并指定动态加载器。这说明目标文件和最终程序具有不同用途：前者供链接器合并代码、处理符号与重定位，后者可以作为程序加载运行。动态链接程序的部分外部函数还需要由动态加载器处理，不能认为链接后所有库函数都已被复制进可执行文件。

`nm build/host/fact.o` 的实际输出为：

```text
                 U __isoc99_scanf
                 U __stack_chk_fail
0000000000000000 T fact
0000000000000036 T main
                 U printf
```

`T` 表示目标文件在代码段中定义了相应符号，因而 `fact`、`main` 是本文件提供的函数。`U` 表示本目标文件引用但未定义该符号：输入调用对应 `__isoc99_scanf`，输出调用对应 `printf`，此外还出现了栈保护相关的 `__stack_chk_fail`。后续实际汇编确认该调用位于 `main` 的返回前检查路径，而非源程序直接编写的调用。这里的符号未定义不代表构建失败，而是链接过程需要处理的外部依赖。

`nm` 中 `fact` 与 `main` 的数值是目标文件中的符号值，不能直接当作程序运行时的绝对地址；`not stripped` 也不能单独证明存在完整调试信息。

证据记录为 `logs/a/file-types.txt` 和 `logs/a/object-symbols.txt`。预处理内容与汇编对应分析分别见后续小节。

### 预处理输出分析

使用 `wc -l` 统计源文件与预处理文件，并提取阶乘函数及主函数对应的片段：

```bash
wc -l src/fact.c build/host/fact.i
grep -n -A35 '^int fact(int n)' build/host/fact.i
```

实际统计结果为源文件 23 行、预处理文件 762 行。`fact` 函数定义出现在预处理文件第 741 行，其循环体仍保留 `while (i <= n)`、`result = result * i` 和 `i = i + 1`；`main` 从第 753 行开始，输入输出及返回语句也仍为 C 代码。

源程序包含 `<stdio.h>`，预处理会展开该头文件及其依赖，并生成源位置标记等内容，因此文本行数显著增加。行数增长不能解释为机器指令数量增加，更不能据此认为预处理阶段已经完成优化或代码生成。抽取片段表明，本例中用户编写的阶乘逻辑在预处理后仍保持源语言形式，后续编译阶段才会将其转换为其他表示。

`grep` 输出中的 `741:` 等是工具添加的匹配行编号，后续行中的 `742-` 等是上下文行编号，不属于实际 C 程序。行数和行号依赖具体头文件与工具版本，不应当作为不同机器上必须一致的验收值。

证据记录为 `logs/a/preprocess-lines.txt` 和 `logs/a/preprocess-source.txt`。

### 宿主机汇编与源程序的对应分析

从实际 `build/host/fact.s` 提取 `fact` 和 `main`。该文件由宿主 GCC 生成，使用 x86-64 的 AT&T 汇编语法，不是 RISC-V 汇编；例如 `movl` 的源操作数在前、目的操作数在后，`$2` 表示立即数。

#### 阶乘函数：局部变量与循环

`fact` 开头以 `pushq %rbp` 保存原帧指针，再用 `movq %rsp, %rbp` 建立当前帧指针。参数通过 `%edi` 进入，并保存到 `-20(%rbp)`；本次局部变量对应关系为：

| 源程序对象 | 本次汇编位置 | 对应操作 |
| --- | --- | --- |
| 参数 `n` | `-20(%rbp)` | `movl %edi, -20(%rbp)` |
| 循环变量 `i` | `-8(%rbp)` | `movl $2, -8(%rbp)` |
| 累乘值 `result` | `-4(%rbp)` | `movl $1, -4(%rbp)` |
| 返回值 | `%eax` | 返回前 `movl -4(%rbp), %eax` |

这些偏移对应本次构建的栈布局，不是变量的固定运行地址，其他编译选项或版本可能生成不同布局。

实际循环核心为：

```asm
        jmp     .L2
.L3:
        movl    -4(%rbp), %eax
        imull   -8(%rbp), %eax
        movl    %eax, -4(%rbp)
        addl    $1, -8(%rbp)
.L2:
        movl    -8(%rbp), %eax
        cmpl    -20(%rbp), %eax
        jle     .L3
```

初始化后的 `jmp .L2` 先执行条件判断，符合 while 的先判断语义。比较前 `%eax` 为 `i`；AT&T 语法下 `cmpl -20(%rbp), %eax` 按 `i - n` 的比较结果设置标志，`jle .L3` 是有符号小于等于时进入循环体，正对应 `i <= n`，不能反读为 `n <= i`。`.L3` 通过 `imull` 计算乘积并存回 `result`，通过 `addl` 将 `i` 加 1，随后顺序进入 `.L2` 再次判断。条件为假时将结果送入 `%eax`，恢复 `%rbp` 并返回。

`fact` 内没有调用其他函数，且未出现额外的 `subq ..., %rsp`，但仍访问当前 `%rsp` 以下的局部存储。这与 System V AMD64 ABI 的 128 字节 red zone 使用规则一致：不跨越函数调用保存的临时数据可以使用该区域。这里并非“没有使用栈”，也不能将这种布局直接搬到 RISC-V。[x86-64 psABI 栈帧规则](https://gitlab.com/x86-psABIs/x86-64-ABI/blob/master/x86-64-ABI/low-level-sys-info.tex)。

#### 主函数：输入、调用与返回路径

`main` 执行 `subq $16, %rsp` 为局部数据留出空间，输入变量 `n` 位于 `-12(%rbp)`。`leaq -12(%rbp), %rax` 计算变量地址，随后放入 `%rsi`；格式字符串地址放入 `%rdi`，再调用 `__isoc99_scanf@PLT`。这与源程序向输入函数传入 `&n` 的操作相对应。

输入调用后的 `cmpl $1, %eax` 与 `je .L6` 检查成功转换项数是否为 1。失败路径将返回值设为 1 并跳到公共退出检查；成功路径从 `-12(%rbp)` 读取 `n`，放入 `%edi`，调用 `fact`。阶乘返回值从 `%eax` 放入 `%esi`，格式字符串地址放入 `%rdi`，再调用 `printf@PLT`，随后将 `main` 的正常返回值设为 0。由于本次只提取了函数区间，没有展示 `.LC0/.LC1` 的定义，不凭函数片段单独断言格式字符串的具体字节。

#### 栈保护：解释目标文件中的外部符号

实际 `main` 入口与退出检查包含：

```asm
        movq    %fs:40, %rax
        movq    %rax, -8(%rbp)
        # 中间为输入、计算与输出路径
.L8:
        movq    -8(%rbp), %rdx
        subq    %fs:40, %rdx
        je      .L9
        call    __stack_chk_fail@PLT
.L9:
        leave
        ret
```

入口保存保护值，返回前将保存值与当前值比较；相等则正常退出，不相等则调用 `__stack_chk_fail`。这解释了目标文件 `nm` 中为什么出现该未定义符号，同时表明该检查不是阶乘算法的一部分。正常和输入失败返回路径都汇合到 `.L8`。本次没有主动破坏栈，因此只观察到了检查代码，未实测保护失败路径。

GCC 文档说明栈保护会在函数入口设置保护值并在退出时检查。实际片段足以确认插入了栈保护，但没有核对当前 GCC 的默认配置，不能仅凭片段确定由哪一个具体默认选项启用。[GCC 11.4 栈保护说明](https://gcc.gnu.org/onlinedocs/gcc-11.4.0/gcc/Instrumentation-Options.html)。

`.cfi_*` 是调用帧信息指令，`.size` 描述符号大小，不应计作执行阶乘逻辑的 CPU 指令。函数开头的 `endbr64` 也不是阶乘运算。证据记录为 `logs/a/host-fact-assembly.txt` 和 `logs/a/host-main-assembly.txt`。

### 词法与语法结构观察

使用 Clang 15 对同一份 `src/fact.c` 输出 token 和 AST，作为 GCC 外部四阶段实验之外的编译器内部表示观察。这里不将 Clang 的 AST 当作 GCC 自身生成的 AST。

```bash
clang-15 -fsyntax-only -Xclang -dump-tokens src/fact.c \
  > logs/a/tokens.stdout 2> logs/a/tokens.txt
clang-15 -fsyntax-only -Xclang -ast-dump \
  -Xclang -ast-dump-filter -Xclang fact src/fact.c \
  > logs/a/fact-ast.txt 2> logs/a/ast-errors.txt
```

#### Token 与源程序的对应关系

筛选 `Loc=<src/fact.c:...>` 的输出，排除头文件中的 token。本次展示的前 35 个源文件 token 包含以下实例：

| 源代码内容 | 实际 token 类别 | 源位置 |
| --- | --- | --- |
| 函数返回类型 `int` | `int` | 第 3 行第 1 列 |
| 函数名 `fact` | `identifier` | 第 3 行第 5 列 |
| 初始化常量 `2` | `numeric_constant` | 第 4 行第 13 列 |
| 循环关键字 `while` | `while` | 第 7 行第 5 列 |
| 比较运算符 `<=` | `lessequal` | 第 7 行第 14 列 |
| 乘法运算符 `*` | `star` | 第 8 行第 25 列 |
| 加法运算符 `+` | `plus` | 第 9 行第 15 列 |

例如，`<=` 被识别为一个 `lessequal` token，而不是两个独立运算符。这体现词法阶段将源字符流识别为记号序列。`Loc` 记录文件、行、列信息；`StartOfLine` 与 `LeadingSpace` 是位置或空白相关标注，不是源语言中的额外 token。由于只展示了前 35 项，不能把该片段误称为完整 token 列表，完整输出保存在 `logs/a/tokens.txt`。

#### AST 的结构与语义信息

本次 AST 输出的根节点为 `FunctionDecl ... fact 'int (int)'`，表明函数返回 `int`、接受一个 `int` 参数。参数由 `ParmVarDecl` 表示，函数体为 `CompoundStmt`。`i` 与 `result` 分别对应初始化为 2 和 1 的 `VarDecl`，初始化常量对应 `IntegerLiteral`。

`WhileStmt` 下包含比较条件和循环体：条件为运算符 `<=` 的 `BinaryOperator`；循环体中，赋值节点 `=` 的右侧分别嵌套乘法节点 `*` 和加法节点 `+`。这种嵌套关系不仅表示出现了哪些 token，也表示表达式如何组合，区别于线性 token 序列。循环之后的 `ReturnStmt` 对应 `return result`。

读取变量 `i`、`n` 或 `result` 时，AST 展示了 `ImplicitCastExpr ... <LValueToRValue>`：例如，比较条件中对 `i` 的引用是一个 `DeclRefExpr` 左值，外层隐式转换表示读取它所代表的值。此处转换前后的类型均为 `int`，不是整数宽度或浮点类型的转换。赋值左侧则直接保留左值引用，用于指定写入对象。

因此，当前 Clang AST 除语法结构外还包含类型、声明引用与隐式转换等语义信息，不能简单描述为未经语义处理的原始语法树。输出中的十六进制节点标识是本次 Clang 进程中的 AST 对象标识，不是实验程序运行时的变量或函数地址。节点类别和结构是分析重点，无需让不同运行的节点地址一致。

上传的终端记录中，打印 `ast-errors.txt` 后没有显示诊断信息，随后正常显示了 `fact` 的 AST；这支持本次观察未显示解析诊断，但该记录没有单独打印 Clang 的退出码，不据此声称已记录所有命令的成功状态。

证据记录为 `logs/a/tokens.txt`、`logs/a/fact-ast.txt` 和 `logs/a/ast-errors.txt`。

### 参考 LLVM IR 生成与观察

以原阶乘源程序为输入，生成未执行中端优化的参考 IR，并进行文本 IR 与 bitcode 的格式转换：

```bash
clang-15 -S -emit-llvm -O0 \
  -Xclang -disable-O0-optnone -fno-discard-value-names \
  src/fact.c -o build/ir/fact_O0.ll
llvm-as-15 build/ir/fact_O0.ll -o build/ir/fact_O0.bc
llvm-dis-15 build/ir/fact_O0.bc -o build/ir/fact_roundtrip.ll
```

`.ll` 是 LLVM IR 文本形式，`.bc` 是 bitcode 形式。终端记录显示这组命令未报告错误；本实验没有逐字比较转换前后的文本，也不要求格式转换后文件字节完全一致。

实际 `fact` 函数签名为 `define dso_local i32 @fact(i32 noundef %n) #0`，使用 `i32` 表示源程序的整数参数与返回值。函数含 `entry`、`while.cond`、`while.body`、`while.end` 四个基本块，控制流依次完成初始化、条件判断、循环更新与返回。

| 源程序含义 | 本次参考 IR 中的表示 |
| --- | --- |
| 参数与局部变量的存储位置 | `entry` 中的 `%n.addr`、`%i`、`%result` 三个 `alloca i32` |
| 初始化参数、循环变量和累乘结果 | `store i32 %n`、`store i32 2`、`store i32 1` |
| 读取变量 | `load i32, ptr ...` |
| 有符号条件 `i <= n` | `icmp sle i32`，比较结果为 `i1` |
| 根据比较结果选择路径 | `br i1 %cmp` 跳到循环体或退出块 |
| 累乘与自增 | `mul nsw i32`、`add nsw i32` 及对应 `store` |
| 循环回边 | `while.body` 末尾跳回 `while.cond` |
| 返回累乘结果 | 退出块中的 `load` 和 `ret i32` |

内存访问使用不透明指针 `ptr`，被读写的值类型由 `load/store` 中的 `i32` 指定。`nsw` 说明相关运算带有不发生有符号溢出的语义约束，而不是一条运行时溢出检查；本例选择 0 至 12 的输入域以避开阶乘整数溢出。

本节讨论的是自动生成的参考 IR，不将它作为手写 LLVM IR 成果。

### SysY 运行库的 RV64 最小测试

### 手写 LLVM IR 与 SysY 运行库验证

#### 构建与对照方法

为避免不同输入输出接口造成干扰，源程序基准 `src/fact_sysy.c` 与手写 IR 路线 `ir/fact_hand.ll` 均调用 `getint/putint/putch`，并链接同一份重新构建的 `build/runtime/libsysy_rv64_linux.a`。`fact_sysy.c` 是供 C 工具链调用 SysY 接口的基准，不据此声称实现了 SysY 编译器。原来的 `src/fact.c` 继续作为宿主机四阶段与参考 IR 实验的输入。

按前一步指导，源程序经 RISC-V 交叉 GCC 生成目标文件并静态链接为 `build/riscv64/fact_source`；手写 IR 路线经过 `llvm-as-15`、`opt-15` 的 verify 检查、`llc-15` 的 RV64 汇编生成，以及交叉 GCC 的汇编和静态链接，得到 `build/riscv64/fact_hand_ir`。当前上传内容直接提供了最终可执行文件检查与运行结果，没有逐条展示这些构建命令的退出码，因此不将构建步骤描述为已独立记录每一步验证状态。

#### 实际源程序与 IR 核对

随后上传的 `src/fact_sysy.c` 内容确认：核心 `fact` 算法仍以 `i = 2`、`result = 1` 初始化，以 `while (i <= n)` 控制累乘和自增；`main` 使用 `getint()` 读取整数，依次调用 `putint(fact(n))` 和 `putch(10)`，最后返回 0。文件只声明所用的三个运行库函数，不包含运行库头文件中的全局对象定义。

本次上传的实际 `ir/fact_hand.ll` 为：

```llvm
target triple = "riscv64-unknown-linux-gnu"

declare signext i32 @getint()
declare void @putint(i32 signext)
declare void @putch(i32 signext)

define signext i32 @fact(i32 signext %n) {
entry:
  br label %loop

loop:
  %i = phi i32 [ 2, %entry ], [ %i.next, %body ]
  %result = phi i32 [ 1, %entry ], [ %result.next, %body ]
  %cond = icmp sle i32 %i, %n
  br i1 %cond, label %body, label %exit

body:
  %result.next = mul nsw i32 %result, %i
  %i.next = add nsw i32 %i, 1
  br label %loop

exit:
  ret i32 %result
}

define signext i32 @main() {
entry:
  %n = call signext i32 @getint()
  %result = call signext i32 @fact(i32 signext %n)
  call void @putint(i32 signext %result)
  call void @putch(i32 signext 10)
  ret i32 0
}
```

`fact` 的四个基本块通过各自末尾的 `br` 或 `ret` 终结。`loop` 的前驱为 `entry` 与 `body`，两个 phi 的前驱标记正与之对应：首次进入时分别取 2 和 1，经回边再次进入时分别取 `%i.next` 和 `%result.next`。循环条件 `icmp sle` 产生 `i1`，而乘法、加法和结果继续使用 `i32`。输入 0 或 1 时从 `loop` 直接到 `exit`，返回初始结果 1。

`body` 定义更新值后回到 `loop`；每个命名 SSA 值在文本中只有一个定义，循环变化由 phi 选择不同迭代的值表达，不需要反复重新赋值同一个 SSA 名称。该函数没有 `alloca/load/store`，这是变量直接以 SSA 值表示的结果，不等同于已证明最终机器码绝不会发生寄存器溢出到栈。

`main` 只有一个基本块，依次读取整数、调用 `fact`、输出结果和换行。声明、定义及调用处的整数参数或返回值保持一致的 `signext` 属性：LLVM 使用该属性表达 ABI 所要求的符号扩展；RV64 中 32 位整数参数与返回值按调用规则扩展到 XLEN。这里不是将整数算法改成 64 位乘法。[LLVM 15 参数属性](https://releases.llvm.org/15.0.0/docs/LangRef.html#parameter-attributes)、[RISC-V 整数调用约定](https://riscv-non-isa.github.io/riscv-elf-psabi-doc/#_integer_calling_convention)。

手写版本与 mem2reg 后的参考 `fact` 在结构上相似，但模块的目标架构、输入输出函数和调用边界不同；手写版本不是将宿主机参考输出直接改名。

### 优化对照实验

执行单独的 `mem2reg` pass，并启用 pass 后的结构验证：

```bash
opt-15 -S -passes=mem2reg -verify-each \
  build/ir/fact_O0.ll -o build/ir/fact_ssa.ll
```

生成参考 IR 时使用 `-disable-O0-optnone`，避免 O0 的 `optnone` 属性阻止所选优化。保留源变量名便于分析，不应把不同机器的自动编号差异视为语义变化。

根据实际上传的 `fact` 函数优化前后片段，统计指令如下；统计范围仅为 `fact`，不是整个模块，也不是最终机器指令：

| 指令 | 优化前数量 | 优化后数量 |
| --- | --- | --- |
| `alloca` | 3 | 0 |
| `load` | 6 | 0 |
| `store` | 5 | 0 |
| `phi` | 0 | 2 |

优化后，参数直接使用 `%n`，循环条件块出现：

```llvm
%i.0 = phi i32 [ 2, %entry ], [ %add, %while.body ]
%result.0 = phi i32 [ 1, %entry ], [ %mul, %while.body ]
```

初次从 `entry` 进入条件块时，两个 phi 分别取初值 2 和 1；从循环体的回边进入时，则取本轮得到的 `%add` 与 `%mul`。phi 按实际进入当前基本块的前驱选择值，不是把两个候选值相加，也不是同时执行两个分支。输入 0 或 1 时，首次判断直接进入退出块，返回的累乘值仍为 1。

优化前的 LLVM IR 也遵循 SSA 的值定义规则，只是可变的源程序变量通过内存槽及 load/store 表示。`mem2reg` 将可提升的内存槽替换为直接使用的 SSA 值和 phi，不应描述为“原 IR 完全不是 SSA”。这里的 SSA 值也不是已经分配好的 CPU 物理寄存器。

本次两个 IR 片段均保留四个基本块和循环回边，变化集中在局部变量表示；没有观察到本轮 pass 将循环展开。没有测量运行时间，因此不根据指令种类变化直接宣称性能提升。源程序中的所有内存对象也不一定都可提升，例如 `main` 中传给输入函数的变量地址需要另行分析，不能将 `fact` 的结论推广为整个模块已无内存访问。

将优化前后 IR 分别编译为宿主机程序：

```bash
clang-15 build/ir/fact_O0.ll -o build/host/fact_from_ir
clang-15 build/ir/fact_ssa.ll -o build/host/fact_from_ssa
```

实际运行结果如下：

| --- | --- | --- | --- | --- |
| 0 | 1 | 1 | 1 | 均为 0 |
| 1 | 1 | 1 | 1 | 均为 0 |
| 5 | 120 | 120 | 120 | 均为 0 |
| 10 | 3628800 | 3628800 | 3628800 | 均为 0 |
| 12 | 479001600 | 479001600 | 479001600 | 均为 0 |

五组输入在三种宿主机构建路径下得到一致结果，为所选测试域内的语义保持提供了实验依据；有限测试不是对所有输入的形式化等价证明。本节只验证宿主机参考 IR 路线，手写 IR 路线的 RV64 实验另见前节，不能将两者混为同一实验。

## 结论

本阶段以同一阶乘逻辑串联了源程序、预处理文本、token、AST、LLVM IR、汇编、目标文件与可执行文件。预处理结果仍是源语言文本；AST 展示嵌套结构与语义信息；IR 以基本块、分支和 SSA 值表达循环；宿主机汇编以栈槽、算术指令和条件跳转实现相同计算。目标文件中的外部符号及 `main` 中的栈保护检查进一步说明，生成代码还包含算法之外的运行库依赖与保护机制。

mem2reg 对照显示，阶乘函数由三个内存槽及相关读写转为两个 phi 和直接 SSA 值，四个基本块和循环回边保持不变。优化前后参考 IR 程序在五组输入下与宿主源程序得到相同结果。调用 SysY 运行库的 RV64 源程序及手写 IR 路线也在相同五组输入下得到预期结果、退出码均为 0，为所列测试下的计算行为保持与目标运行链路提供了证据。

结论限于已记录的整数测试和实际观察：尚未覆盖全部有效输入，也没有验证浮点、数组、逻辑短路或保护失败路径，不给出性能优劣判断。本节可作为成员 A 的核心实验结论；整组实验仍需结合成员 B 的手写 RISC-V 汇编与交叉复现结果撰写最终结论。
