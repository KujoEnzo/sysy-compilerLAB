## 运行库处理

### 原始库与 Linux 路线

教师材料中的 `libsysy_riscv.a` 经前期检查为 ELF64 RISC-V 归档，并出现 `_impure_ptr` 未定义引用，说明它可能依赖 Newlib 的重入状态。当前实验路线使用 Ubuntu 的 `riscv64-linux-gnu-gcc` 和 glibc，因此不直接把该预编译归档与 Linux 工具链混用，也不通过伪造 `_impure_ptr` 绕过依赖。

将教师压缩包解压到 `vendor/` 后，以教师原始 `vendor/lib/sylib.c` 重建一个名称不同的 Linux 运行库：

```bash
riscv64-linux-gnu-gcc -march=rv64gc -mabi=lp64d \
  -mcmodel=medany -O0 -c vendor/lib/sylib.c \
  -o build/runtime/sylib_rv64_linux.o
riscv64-linux-gnu-ar rcs build/runtime/libsysy_rv64_linux.a \
  build/runtime/sylib_rv64_linux.o
```

仓库中的 `make runtime` 封装了相同步骤。新库命名为 `libsysy_rv64_linux.a`，不会覆盖教师提供的原始归档。若课程验收明确要求 `riscv64-unknown-elf` 与原始库，应改用教师配套工具链并单独建立目标，不能将两条 libc 路线混合。

### 最小接口测试

`src/runtime_smoke.c` 只执行“读取一个整数、原样输出、输出换行”，用于在阶乘汇编之前隔离验证运行库、链接器和 QEMU。成员 A 已实际记录输入 42 时 stdout 为 `42\n`、退出码为 0，stderr 为 `TOTAL: 0H-0M-0S-0us`。这证明当时的 RV64 Linux 运行库最小链路可用，但只覆盖三个整数 I/O 接口。

`Makefile` 的 `smoke` 目标会再次运行同一检查，并按字节比较 `tests/expected/smoke.stdout`。stdout 是程序答案；运行库写入 stderr 的 `TOTAL: ...` 被单独保存，不作为答案，也不把真正的诊断信息丢弃。

## 手写 RISC-V 汇编

### 阶乘函数

`asm/fact_hand.s` 中的 `fact` 是叶函数。根据 RISC-V 整数调用约定，第一个整数参数和返回值均经 `a0` 传递。函数不调用其他函数，只使用调用者保存的临时寄存器 `t0`、`t1`，因此不建立栈帧：

```asm
fact:
        li      t0, 2
        li      t1, 1
.Lfact_loop:
        blt     a0, t0, .Lfact_done
        mulw    t1, t1, t0
        addiw   t0, t0, 1
        j       .Lfact_loop
.Lfact_done:
        mv      a0, t1
        ret
```

寄存器与程序对象的对应关系如下：

| 程序对象 | 寄存器 | 说明 |
| --- | --- | --- |
| 参数 `n` | `a0` | 循环期间保持原参数，退出时改放返回值 |
| 循环变量 `i` | `t0` | 初值 2，以 `addiw` 按 32 位整数递增 |
| 累乘结果 `result` | `t1` | 初值 1，以 `mulw` 按 32 位整数相乘 |

源程序条件为 `i <= n`。汇编将其等价改写为“若 `n < i` 则退出”，即 `blt a0, t0, .Lfact_done`。`blt` 使用有符号比较，符合 C/SysY 的 `int` 语义。输入 0 或 1 时首次比较就退出并返回初值 1；输入 5 时依次乘 2、3、4、5。

使用 `mulw` 和 `addiw` 而不是 RV64 的全宽 `mul`、`addi`，使低 32 位运算结果按规则符号扩展回 XLEN，与本实验的 32 位 `int` 表示保持一致。测试域不包含有符号整数溢出，因此不讨论溢出后的语言语义。

### 主函数、返回地址与栈对齐

`main` 依次调用 `getint`、`fact`、`putint` 和 `putch`，属于非叶函数。每次 `call` 都会覆盖 `ra`，所以入口将 `ra` 保存到栈，返回前恢复：

```asm
main:
        addi    sp, sp, -16
        sd      ra, 8(sp)
        call    getint
        call    fact
        call    putint
        li      a0, 10
        call    putch
        li      a0, 0
        ld      ra, 8(sp)
        addi    sp, sp, 16
        ret
```

栈空间一次减少 16 字节，保证调用边界的 `sp` 仍按 16 字节对齐。函数未使用 `s0` 至 `s11` 等被调用者保存寄存器，因此无需额外保存。`getint` 和 `fact` 的返回值直接留在 `a0`，作为下一次调用的第一个参数；`putint` 返回后不再依赖任何调用者保存寄存器。

### 伪指令与真实指令

源文件为增强可读性使用了 `li`、`mv`、`j`、`call` 和 `ret` 等汇编器伪指令。它们不是各自独立的 RISC-V 基础编码：小立即数 `li` 通常展开为 `addi`，`mv` 可展开为 `addi rd, rs, 0`，`j` 可展开为 `jal x0, label`，`ret` 可展开为 `jalr x0, 0(ra)`。`call` 根据目标距离、重定位和链接松弛可能由 `auipc`/`jalr` 组合或更短调用实现。因此报告中的机器级结论应以 `objdump -dr` 和链接后 `objdump -d` 的实际输出为准，不能只根据伪指令文本猜测最终编码。

## 构建与统一测试

项目根目录的主要命令为：

```bash
make check-tools
make environment
make test
make inspect
```

`make test` 完成以下链路：

1. 从教师 `sylib.c` 重建 RV64 Linux 静态运行库。
2. 编译并运行最小 I/O 测试。
3. 分别生成源程序、手写 LLVM IR、手写汇编三个静态 RV64 可执行文件。
4. 对三个程序分别输入 0、1、5、10、12，共执行 15 次。
5. 逐字节比较实际 stdout 与带换行的期望文件，检查退出码，并分别保存 stderr。
6. 用实际结果覆盖 `tests/results.md`；任何一次输出不符或退出码非 0，脚本返回失败。

LLVM IR 路线先由 `llvm-as` 解析为 bitcode，再使用 `opt -passes=verify` 验证，随后由 `llc` 生成 RV64 汇编。三条路线最终均通过同一交叉 GCC 静态链接同一运行库，减少工具链、库和输入差异对对照结果的干扰。

默认 LLVM 工具名按 A 的实际 Ubuntu 环境设置为 15 版。使用 LLVM 18 时显式覆盖：

```bash
make LLVM_AS=llvm-as-18 OPT=opt-18 LLC=llc-18 test inspect
```

## 汇编与链接观察

`make inspect` 分别保存手写汇编目标文件的带重定位反汇编和最终静态可执行文件的反汇编。两者用途不同：目标文件中对 `getint`、`putint`、`putch` 的调用尚待链接，`objdump -dr` 可以同时显示指令与重定位；链接后符号已被解析，且链接器可能执行指令松弛，因此最终调用序列和地址必须从链接后文件观察。

仓库已有 LLVM 自动生成的参考 `docs/reference/fact_hand_rv64.s`。文本对照可见，自动版本在 `fact` 中使用 `a1` 保存 `n`、`a0` 保存累乘结果、`a2` 保存循环变量，并将循环组织成一次入口判断加底部回跳；手写版本在退出前一直保留 `a0=n`，使用 `t0/t1` 表示循环变量与结果，并采用顶部退出判断。两者控制流布局和寄存器分配不同，但都表达相同的有符号循环条件和 32 位乘法。该文本分析不是性能比较；只有在相同选项下取得反汇编和测量数据后，才能讨论代码大小或速度差异。

## 小结

本部分给出了与 A 的源程序和手写 IR 对齐的 RV64 手写汇编。`fact` 遵循整数参数和返回值经 `a0` 传递的规则，以 `mulw/addiw` 保持 32 位整数运算，并使用有符号分支实现 `i <= n`；`main` 保存 `ra` 且保持 16 字节栈对齐。统一 Makefile 与测试脚本把三条路线连接到同一运行库，按字节验证 stdout，并独立记录 stderr 和退出码。

现有 A 日志证明源程序、手写 IR 和最小运行库测试在其 Ubuntu 环境中通过；B 新增的手写汇编仍需在同一类环境生成实际反汇编与 QEMU 日志。最终结论应以该次真实运行证据为准，而不是以静态分析代替执行结果。
